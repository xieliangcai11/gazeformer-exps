## 一、已确认的结论

### 1.1 当前基线（唯一有效的参照点）

| 模型 | 配置 | test_em | 角度(均) | ≤1.91° | n |
|---|---|---|---|---|---|
| G5 | 448 / no-depth / aug / 10 epoch | 1.68 cm | — | — | 11031 |
| **G6** | 448 / no-depth / aug / 30 epoch | **1.67 cm** | **3.14°** | **33.1%** | 11031 |
| 论文 RGBDGaze 基线 | — | 1.89 cm | — | — | — |
| MAC-Gaze（2026） | 骨干 + 运动感知持续校准 | 1.41 cm | — | — | — |

**结论**：无校准已超论文基线 **11.6%**，但未达 MAC-Gaze。

> **G6 的 1.67cm / 3.14° / 33.1% 是此后一切改进的唯一裁判线。**
> 任何新方法（校准 / 预训练 / 几何）必须超过它才算正收益，否则一律记为负面提升。

### 1.2 校准路线已系统性排除

| 方法 | 结果 | 判定 |
|---|---|---|
| Ridge 回归（10% / 15% 校准数据） | 1.67 / 1.84 cm | ❌ 无改善或恶化 |
| 线性 / 仿射校准 | 1.84 ~ 2.51 cm | ❌ 全部恶化 |
| MLP 全映射校准 | 崩溃 | ❌ |
| 按姿势（sitting/standing/walking/lying）校准 | 2.48 cm | ❌ |
| 按姿势 + IMU 校准 | 2.50 cm | ❌ |
| VPT（4 个 prompt token，1536 参数） | p39 +22~36%，其余 4 人 −3.8%~+0.3%；同口径整体 2.08→1.99（+4.3%） | ⚠️ 只对"本来就差的人"有效，无整体价值 |

**结论**：校准只能在**输出端打补丁**，修不了"特征空间本身缺少注视先验"。
这一步把问题从"校准没做对"改判为"骨干没见过足够多的人"。

### 1.3 根因诊断

```
训练集 36 人 → 中位误差 0.33cm（几乎完美）
测试集  5 人 → 中位误差 1.46cm（差 4 倍）
+ 所有校准方法失败
⇒ 模型对 36 个训练被试过拟合，对新用户的特征空间没有注视先验
⇒ 必须引入大规模多用户数据做预训练（GazeCapture: 1474 人 / 244 万帧，
  其中约 149 万帧人脸+双眼检测齐全 —— 即我们预处理后实际可用的子集）
```

### 1.4 GazeCapture 数据管线已可用（已验证）

**坐标系结论（重要且反直觉）**：

- 4 种 orientation 下图像人脸滚转角中位数 `+0.0° / +0.0° / +3.8° / -2.3°`，100% 落在 ±30° 内 → 图像本身就是"人脸正立"；
- 对**同一屏幕尺寸**拟合 `(XPts,YPts) → (XCam,YCam)`，四种朝向得到**完全相同**的变换（`M ≈ diag(+s, -s)`，列角度 0°/-90°）。

⇒ **图像坐标系与标签坐标系天然对齐，无需任何旋转**，直接按 bbox 裁剪即可。与官方 `pytorch/prepareDataset.py` 不旋转的做法一致。

**抓出并修掉 2 个真实换算 bug**（用官方设备表算出的 cm/点 与实测拟合互相比对时暴露）：

| 问题 | 表现 | 修正 |
|---|---|---|
| 显示缩放（Display Zoom）未处理 | iPhone 6 帧 `screen_w=320` 却用非缩放的 375 做分母 | 按帧的 W/H 匹配缩放点数 |
| 横屏物理尺寸未互换 | iPad 1024×768 横屏算成 (0.0200, 0.0198)，应为 (0.0198, 0.0200) | 在「标准/缩放 × 竖屏/横屏」四种组合中匹配 |

修正后全部与实测拟合逐位吻合，`cm_scale_unmatched = 0`。

**`dump_checks.py` 全操作留痕工具**：24 样本 × 29 类一致性断言 **696/696 PASS**，把每一步中间量 + 多面板图像落盘供人工复核。

### 1.5 两个数据集的差异（量化，决定泛化难度）

| 维度 | GazeCapture | RGBDGaze | 关系 |
|---|---|---|---|
| **屏幕宽高比** | 0.562 / 0.563 / 0.750（仅 3 个取值） | **0.462** | **外推**（窄 22%） |
| 物理屏宽 | 5.17 ~ 20.31 cm | 6.42 ~ 7.81 cm | 内插 ✅ |
| 人脸框/帧短边 | 中位 0.467，5~95% 0.352~0.789 | 中位 0.427，0.312~0.591 | GC 方差 **2.2 倍** |
| 图像 | 480×640 VGA（2016 年机型） | 1080×1440（现代 TrueDepth） | 光学差异 |
| 目标分布 | 离散网格（每被试 16~480 个点） | 连续动画（36725 个去重点） | 微调可消化 |
| 深度 | ✗ 无 | ✓ 有（但已证无效） | 已删 |
| IMU 重力 | ✓（DotNum+Time 对齐，匹配率 100%） | ✓ | 约定一致 |
| 标签分布 / 非镜像 / 旋转后帧宽高比 | — | — | **一致** ✅ |

**关键点**：GazeCapture **没有一款 19.5:9 的现代全面屏手机**，宽高比这一维是纯粹的"没见过"。

### 1.6 深度模态：已彻底移除

实验证明在 RGBDGaze 上无正收益。已删除：`DepthAttentionFusion` / `DepthPatchEmbed` / `use_depth` / `depth_mode` / `inverse_depth_preprocess` / `depth_preprocess` / 索引 `depth_path` 列，以及旧 CLIP+ResNet 双流基线整套（`rgbdgaze.py` + `train_baseline.py` + `predict.py`，其唯一存在理由就是深度融合）。

**共 −1002 行。** 预训练阶段也相应关闭深度分支（正好对应当前最优的 G5/G6 `nodepth`）。

### 1.7 几何泛化：P0 + P2 已实现，物理机制已验证

**P2 的物理基础（独立校验通过）**——反解"相机在屏幕上的归一化位置" u_c，发现它对同一机型是**严格常数**（标准差 0.0000），且横向尺度严格等于屏幕物理宽：

| 设备 | 反解 u_c | 标准差 | 用**一半帧**拟合 u_c → 预测**另一半帧**的 XCam（中位 / 95%） |
|---|---|---|---|
| iPad Air 2 | 0.5000 | **0.0000** | 0.0000 / **0.0010 cm** |
| iPhone 5 / 5S | 0.5000 | **0.0000** | 0.0000 / **0.0000 cm** |
| iPhone 6 | 0.3181 | **0.0000** | 0.0000 / **0.0000 cm** |

由此得到标签重投影的**精确闭式解**（相机相对屏心位置不变、只换屏幕尺寸）：

```
u' = 0.5 + (u - 0.5) · (W_cm / W')
v' = 0.5 + (v - 0.5) · (H_cm / H')
```

**真实物理标注不变，只有"假设的屏幕形状"是合成的，不属于编造数据。** 该变换可把宽高比这一维从**外推**变成**内插**。
合成宽高比范围取 **(0.40, 0.58)** —— 上限取 0.58 而非 0.80 是因为真实数据已覆盖
0.562/0.563/0.750，把一半合成预算花在 0.56~0.80 只是重复已有分布。实测：
范围 (0.40,0.80) 时合成几何落在 <0.562 的仅 51%（占全部样本 15.7%）；
范围 (0.40,0.58) 时达 89%（占全部样本 **27.6%**），生效率基本不变（61.6%→61.8%）。

其余验证：恒等（合成几何 = 真实几何）标签逐位不变（偏差 0.0）；缩放-反缩放往返误差 1.2e-7（float32 精度）；`geom_randomize=0` 时与真实标签一致（2.98e-08）。

**几何敏感性是真实存在的**（实测，无几何 token 的 G6，同一批帧只换合成几何）：

| 合成宽高比 | EM | 相对 0.462 |
|---|---|---|
| 0.462（真实 19.5:9） | 1.143 cm | — |
| 0.550（16:9） | 1.268 cm | +11% |
| 0.700（4:3） | 1.402 cm | **+23%** |

> 读法：不同 aspect 之间的**绝对值不可横向比较**（合成屏尺寸不同会让标签整体缩向屏心）。
> 正确用法是在**同一 aspect** 下比较"带几何 token"与"不带几何 token"的模型。

### 1.8 一个方法学结论（很重要）

RGBDGaze test 集的**设备与被试完全混淆**（p11↔iPhone12Pro Max、p24↔XR、p31↔12 Pro、p33↔12、p39↔12 Pro Max），按设备拆和按被试拆得到**逐位相同的数字**：

| 分组 | EM (cm) | 1.374 | 1.596 | 1.721 | 2.168 | 2.788 |
|---|---|---|---|---|---|---|
| 被试 | | p11 | p33 | p24 | p39 | p31 |
| 设备 | | 12PM | 12 | XR | 12PM | 12 Pro |

⇒ **现有划分根本无法分离"设备效应"与"个人效应"**；要测跨设备泛化，必须重建留一设备划分并**重训**。
⇒ 同时看到：**最大的误差源是"人"（1.37→2.79，2 倍差），不是"设备"**。

### 1.9 尚未验证的（必须说清）

> **P0（几何 token）与 P2（几何域随机化）目前一次训练都没跑过，零个已测得的提升。**
> 已交付的是：机制 + 工具 + "机制本身在物理上正确"的验证。
> 有效与否只能靠实验清单里的**实验 4** 判定。

另：P1 的基线复现证明工具口径无误 —— `cross_eval` 在 RGBDGaze test（11031 帧）上给出
**EM 1.673cm / 角度 3.14° / ≤1.91° 33.1%**，与训练期验收数字完全一致。

## 二、下一步：详细计划

```
阶段1 全量预处理 + 体检  →  阶段2 预训练  →  阶段3 微调
                                              │
                                    test_em < 1.67cm ?
                                       ├─ 否 → 失败预案（P3/P4/P5）
                                       └─ 是 → 阶段4 交叉评估矩阵 → 阶段5 消融 → 阶段6 结论
```

### 阶段 1：GazeCapture 全量预处理 + 数据体检（服务器，约 1~2 小时）

```bash
# 1) 解压 1474 个 tar.gz（244 万帧；预处理后约 149 万帧可用）
python tools/data/gazecapture/preprocess.py --extract

# 2) 抽样留痕复核（确认索引与裁剪无误，可人工比对）
python tools/data/gazecapture/dump_checks.py --num-samples 60 --augment
```

产出：`data/GazeCapture/index/{index.csv, train.txt, val.txt, test.txt, summary.txt}` + `out/gazecapture/preprocess/logs/*.txt`。

**体检清单（每项都会影响采样策略）**：

| 检查项 | 为什么重要 | 期望 |
|---|---|---|
| 各机型帧数分布 | 当前 11 被试样本是 **iPad 占 58%**，全量应反过来 | 确认是否需要按机型均衡采样 |
| 被试帧数 < 10 的数量 | `MIN_VALID_FRAMES_PER_SUBJECT=10`，会被整段丢弃 | 记录丢弃比例，评估数据损失 |
| 朝向分布 | 横屏约占 33%（RGBDGaze 全是竖屏） | 决定是否只留竖屏预训练 |
| `cm_scale_unmatched` | 设备不在规格表 ⇒ cm 换算为 NaN | 应为 0；非 0 则补 `DEVICE_ALIASES` |

### 阶段 2：GazeCapture 预训练（约 5~8 小时 GPU）

```bash
# 224 比 448 快约 4 倍（先验证路线是否成立，再谈精度）
# --geom：屏幕几何 token（P0）；--geom-randomize：几何域随机化（P2），把"宽高比外推"变成"内插"
# 注意：注释不能放在 `\` 续行的同一行，否则续行会被破坏（剩余行会被当成独立命令）
python -m scripts.train --dataset gazecapture \
    --index-dir data/GazeCapture/index \
    --resolution 224 \
    --geom \
    --geom-randomize 0.5 \
    --augment --aug-rotate 10 --unfreeze 12 \
    --epochs 3 --tag gc_pretrain
```

**成本核算**（按 G5/G6 实测吞吐外推）：127k 帧 @448 约 34 分钟/epoch；
预处理后约 149 万帧 @224 约 **1.7 小时/epoch** ⇒ 3 epoch ≈ 5 小时。
（若只留竖屏可再省约 1/3。）

**分辨率迁移（224 预训练 → 448 微调）**：`unfreeze_last=12` 只解冻最后 12 个 block，
`pos_embed` 保持冻结，所以分辨率变化不改动任何已学权重。

⚠️ 但**不是原样就能加载**：checkpoint 里的 `pos_embed` 是 16x16 网格 `[1,257,384]`，
而 448 模型要 32x32 网格 `[1,1025,384]`，`load_state_dict(strict=False)` 只豁免
"键缺失/多余"，对形状不匹配仍抛 RuntimeError（实测：
`size mismatch for rgb.backbone.pos_embed`）。现由 `load_state_dict_any_res()`
按目标网格自动插值（口径与加载官方 DINOv2 权重完全一致），并把这行写进日志。
服务端用真实权重验证通过：

```
[init] pos_embed 分辨率不一致 (1, 257, 384) -> (1, 1025, 384)，已插值
[init] 缺失键 无 | 多余键 无
```

**验收标准**：GazeCapture 自身的 `val_em` 随 epoch 下降并趋于平稳。若第 2 epoch 就不再下降 → 预训练见顶，提前停，直接进阶段 3。

### 阶段 3：RGBDGaze 微调（约 2 小时）

```bash
# --init-ckpt 必须显式给出：否则这次微调就是从 DINOv2 原始权重从零开始，
#   阶段2 的预训练完全白做，还会得出"预训练没用"的错误结论。
# 下面用的是已经跑完的那次预训练（val_ang 4.11°）；若你按阶段2 的命令重跑，
#   改成你自己的 --tag 目录即可。
# 预训练是 224、这里是 448，pos_embed 会自动插值（见上节），无需额外操作。
python -m scripts.train --dataset rgbdgaze \
    --index-dir data/RGBDGaze/index \
    --init-ckpt out/gazecapture/ablation/checkpoints/gc_pretrain_6gpu/best.pt \
    --resolution 448 --geom --augment --aug-rotate 10 --unfreeze 12 \
    --epochs 8 --tag gc_pretrain_ft
```

> 训练入口已就绪：`scripts/train.py` 加了 `--dataset {rgbdgaze,gazecapture}`、`--init-ckpt`
> 与 `--geom-randomize`（几何域随机化强度，缺省取各自 config），
> 两个数据集共用同一条训练循环（只有数据集构造与索引路径不同，评估口径完全一致）。
> 已本地冒烟验证：GazeCapture 训练路径跑通；从预训练权重微调 RGBDGaze 时
> **缺失键 无 | 多余键 无**（两边都开几何 token、都无深度，权重完全对齐）。

**验收标准**：

| 结果 | 判定 | 下一步 |
|---|---|---|
| `test_em` **< 1.67cm** | ✅ 主路线成立 | 进阶段 4 |
| `test_em` ≈ 1.67cm | ⚠️ 预训练没带来新先验（域差异过大） | 走失败预案 P3 |
| `test_em` > 1.67cm | ❌ 负迁移 | 检查冻结骨干 / 降 lr / 减小预训练权重影响后重试 |

### 阶段 4：交叉评估矩阵（每项 5~40 分钟）

```bash
# ① 域内：新模型 vs G6（基线 1.673cm）
python -m scripts.cross_eval --protocol domain --ckpt <g6.pt> <新模型.pt>

# ② 留一设备：先出清单，再用该目录重训，再评估
python -m scripts.cross_eval --protocol leave-device --holdout "iPhone 11" \
    --write-split out/rgbdgaze/cross_eval/leaveout_iPhone11

# ③ 跨数据集零样本：GazeCapture 预训练权重直接测 RGBDGaze
python -m scripts.cross_eval --dataset rgbdgaze --protocol domain \
    --ckpt out/gazecapture/pretrain/best.pt --all-splits --limit 5000

# ④ ⭐ 几何外推：P0/P2 的决定性证据
python -m scripts.cross_eval --protocol domain --geom-shift 0.462 0.55 0.70 \
    --ckpt <不带geom的老权重> <带geom的新权重>
```

**第 ④ 项是全项目最关键的一张表**：

| | aspect 0.462 | 0.55 | 0.70 | 结论 |
|---|---|---|---|---|
| 不带 geom token（已实测） | 1.14 | 1.27 | 1.40 | 随几何偏移单调变差 |
| **带 geom token（期望）** | ~平稳 | ~平稳 | ~平稳 | ⇒ P0/P2 有效 |
| 带 geom token（若也变差） | — | — | — | ⇒ 几何 token 白加了，需改设计 |

### 阶段 5：消融

| 消融 | 回答的问题 |
|---|---|
| `--geom` vs `--no-geom` | 屏幕几何 token 有没有用 |
| `--augment`（几何抖动）开/关 | 抹平人脸框分布差异有没有用 |
| `geom_randomize` 0 / 0.35 / 0.5 | 几何域随机化的最佳强度 |
| GazeCapture 预训练 vs 从头训 | **预训练这条路本身值多少** |

## 三、失败预案（若阶段 3 没超过 1.67cm）

| 优先级 | 手段 | 依据 |
|---|---|---|
| **P3** | 图像降质增强：随机高斯模糊 σ∈[0,1.5]、高斯噪声、随机降采样到 0.5~1.0 倍 | GazeCapture 是 2016 年 VGA 摄像头，与 RGBDGaze 的锐度差异是域间隙之一 |
| **P3'** | 采样均衡：预训练时按机型/被试均衡，避免 iPad 横屏主导 | 当前样本里 iPad 占 58%，全量分布需实测确认 |
| **P4** | 相机系标签：预测 `XCam/YCam`（cm，相对相机），推理时再用设备几何转回屏幕坐标 | 从根上消除标签对屏幕几何的依赖；代价是要处理两边相机内参 |
| **P5** | 只留竖屏预训练（去掉约 33% 横屏） | 减少与 RGBDGaze 无关的分布 |

## 附录 A：关键指标口径

| 指标 | 含义 | 说明 |
|---|---|---|
| `em_dist` | 屏幕欧氏误差（cm） | 由归一化误差 × 屏幕点数 × 每点厘米得到；论文对标口径 |
| `ang_mean/median` | 几何视线角度（度） | 假设眼到屏基准距离 30cm 的近似口径 |
| `ang_ratio_le_191` | 角度 ≤ 1.91° 的占比 | 越接近人眼精度上限越好 |
| `≤1.91°` 阈值 | 约等于屏幕中心 1cm 的对应角度 | 用于与论文/产品口径对齐 |

**换算关系**：`cm 误差 = |归一化误差| × 屏幕点数 × 每点厘米`；每点厘米来自官方设备规格表（`tools/data/gazecapture/apple_device_data.csv` / `data/RGBDGaze/RGBDGaze_dataset/iphone_spec.csv`）。

```
总有效样本 1,490,911 / 被试 1,463     （官方 README：1,490,959 帧检测齐全，差 48 = 0.003%）

| 检查项 | 结果 | 判读 |
|---|---|---|

| `drop_invalid_detection` | 954,545 | 加可用帧 = 2,445,456，对官方 2,445,504 差 48（0.002%） |
| `drop_missing_frame` / `drop_degenerate_bbox` | 0 / 0 | 无坏帧 |

**设备分布**：iPhone 合计 **85.3%**（iPhone 6 27.8% + 5S 24.1% + 6 Plus 9.9% + 6s 9.5% + …），
iPad 14.7%。→ 全量以手机为主，与 RGBDGaze（纯手机竖屏）接近；
**此前基于 11 被试样本"iPad 占 58%"的采样均衡担忧不成立**。

**朝向分布**：竖屏 38.1% + 竖屏倒置 3.7% + 横屏 **58.2%**。
→ 这是全量数据最大的分布错位（RGBDGaze 是 100% 竖屏）。
实测几何随机化在横屏上生效率并不低（55~59%，与竖屏 74% 同量级），
故**先按全量跑**；若收敛受拖累，再试"只留竖屏"的对照。

**几何域随机化的实际效果**（按全量朝向占比加权）：
触发时生效率 **63.0%** → ×`GEOM_RAND_PROB=0.5` ⇒ **31.5%** 的帧被重投影，
其中 89% 落在 aspect<0.562 ⇒ **约 28% 的帧在教模型"窄屏"**（目标 0.462 所在区间）。

## 附录 E：多卡训练卡顿根因与修复（2026-10-12）

**根因**：索引 CSV 用 `list(csv.DictReader(f))` 读入 = 每行一个 dict。

| | 数值 |
|---|---|
| 实测每行开销 | 1,538~1,927 B |
| GazeCapture train 划分 1,251,935 行 | **2.41 GB / 进程** |
| DataLoader fork 出的 worker | 引用计数写操作触发**写时复制**，随 worker 数成倍膨胀 |

**修复**（`gazelab.datasets.table_index.TableIndex`，列式存储 + 按需构造 dict）：

| | 修复前 | 修复后 |
|---|---|---|
| 常驻 | 2.41 GB | **0.28 GB**（8.6×） |
| 构造峰值 | 2.41 GB | 0.37 GB |
| 取值一致性 | — | 与 `DictReader` 逐列逐行完全一致（含 `subject="00002"` 前导零） |

**同时处理的其它来源**：
- `path_to_idx` 的 `{r[col]: i for i, r in enumerate(rows)}` → `TableIndex.lookup()`（原来瞬时 2.4GB 峰值）
- DataLoader 加 `persistent_workers=True` + 显式 `prefetch_factor`（避免每 epoch 重新 fork）
- `cross_eval` / `bias_decomposition` 各自的 `DictReader` 一并换掉

**已记录的未改动项**：RGBDGaze 自带的 `iphone_spec.csv` 中 `w_cm/h_cm` 是**机身尺寸**而非
屏幕尺寸（iPhone12 Pro Max 7.81×16.08cm = 机身 78.1×160.8mm，而其 `inch=6.68"` 对应屏幕对角），
与自身列自相矛盾，使 cm 误差被系统性放大约 10%。因与论文同表、相对比较仍有效，故未擅改。
